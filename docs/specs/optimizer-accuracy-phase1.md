# 243基地ローテーション最適化・精度改善 Phase 1 実装仕様書

## 1. 文書情報

- 状態: 改訂承認済み仕様
- 改訂日: 2026-08-06
- 対象プロジェクト: `arknights-basement-simulator`
- 対象フェーズ: Phase 1
- 主対象地域: 日本版（JP現行版）
- 副対象地域: 中国版（CN最新版）
- 実装チケット: 本仕様の承認後、別工程 `to-tickets` で作成する
- 補足仕様: `optimizer-normalized-theoretical-scenarios.md`。本書がPhase 1のauthorityであり、補足仕様は本書を置換しない。評価窓、schedule、資源台帳、持続性、confidence、出典固定、地域gate、hardcode禁止が食い違う場合は本書を優先する

## 2. 背景

現行シミュレーターは、基地スキルを正規化したデータとブラウザ内の探索ロジックを用いて配置案・2交代案を生成している。陣営、同室、指定オペレーター、施設間効果、時間変化、体力、特殊注文などの一部は個別モデル化されているが、READMEでMVPモデルと明記されており、外部で検証された理論編成・理論生産量との体系的な照合基準がない。

現行の構造監査は、効果値の欠落や未分類効果などを検出できる一方、次の誤りを検出できない。

- スキル文言の意味解釈が誤っている
- 正しい値を誤った条件・対象・加算順序で適用している
- 時間、体力、注文確率、ドローンを含む24時間換算が誤っている
- 個々のスキル計算は正しくても、探索が理論上優れた編成を候補から落としている
- JP版とCN版の利用可能オペレーターが混在している

Phase 1では、外部根拠を版管理された基準ケースへ変換し、現行出力との差分を再現可能にしたうえで、データ解釈、計算モデル、探索アルゴリズムを分離して検証・修正する。

## 3. 目的

1. 243基地について、出典が明示する日界または順序付き全循環の最初の勤務枠からの具体的な連続24時間を、12時間×2勤務枠または8時間×3勤務枠で評価し、資源別生産量を一貫した期待値モデルで算出する。
2. JP現行版の全員所持・基地スキル全解放条件で、公開された理論編成または同値編成を選択できるようにする。
3. 限定所持条件でも、利用可能なオペレーターだけから再現可能で妥当な最適編成を生成する。
4. スキル解釈、計算式、探索結果を、それぞれ独立した自動テストで検証できるようにする。
5. 外部根拠、前提、期待値、未確定事項を追跡可能な形式でリポジトリに保存する。
6. JP版とCN版のベンチマークを混在させず、独立して更新・検証できるようにする。

## 4. 対象外

Phase 1では次を実装しない。

- 153基地の最適化
- 交代時刻そのものを探索する可変ローテーション
- 12時間×2勤務枠および8時間×3勤務枠以外のローテーション
- 計算根拠、出典、信頼度を結果画面へ表示するUI
- 全施設を独立した成果指標として最適化する機能
- 外部Wikiをテスト実行時に取得するオンラインテスト
- ゲーム内操作遅延、在庫停止、全支援施設の連続morale推移を含む完全な実ゲーム再現
- Phase 1の完了条件としてゲーム内24時間ログとの一致を要求すること
- デプロイ、公開、Git commit、push、Pull Request作成、merge

ただし、製造所・貿易所の出力へ影響する制御中枢、発電所、宿舎、応接室などの配置・スキルは、必要な範囲で計算対象に含める。

## 5. 用語

### 5.1 基準ケース

外部根拠、入力条件、期待編成、期待計算式、期待生産量を固定した、ネットワーク非依存のテストケース。

### 5.2 理論編成

対象サーバー・対象バージョン・所持条件・施設構成・交代条件のもとで、外部資料により最適または最適候補として提示され、計算根拠を確認できた編成。

### 5.3 同値編成

オペレーターの並び順や同効率の代替要員などが異なっていても、すべての制約を満たし、対象となる資源別24時間生産量が許容差内で一致する編成。

### 5.4 持続可能

各オペレーターが担当シフトを完了でき、次に担当するまでに必要な体力を回復でき、同一時刻に複数施設へ配置されず、金属在庫など生産継続に必要な資源制約を満たす状態。

### 5.5 JP現行版 / CN最新版

基準データに記録された参照日時点で、各地域のゲーム内で利用可能なオペレーター・基地スキル・仕様を指す。「最新版」を暗黙に現在時刻へ追従させず、各基準ケースにデータ版または参照日を固定する。

### 5.6 24時間評価窓

出典が明示する日界、または固定された順序付き全循環の最初の勤務枠から始まる、具体的な連続24時間。36時間・48時間などの全循環平均を24時間換算した値は、24時間評価窓の実値として扱わない。

### 5.7 勤務枠

24時間評価窓を等分した1回の連続勤務時間。2勤務枠モデルでは1枠12時間、3勤務枠モデルでは1枠8時間とする。勤務枠数は勤務グループ数を意味しない。

### 5.8 全循環周期

体力消費、宿舎回復、勤務者の交代を含め、同じ運用状態へ戻るまでの周期。24時間評価窓を超えてよいが、採用する編成出典に周期全体が明示されていなければならない。

### 5.9 出典固定

固定コミット、または内容ハッシュを記録した保存済みスナップショットによって、取得後の差し替えから根拠を保護すること。参照日だけを記録した可変URLは、固定済み出典とはみなさない。

### 5.10 corroborated合否基準

固定外部編成と一次ゲームデータを基礎にしつつ、一次根拠が欠ける数量則を、版固定したプロジェクト仮定で補完する合否基準。再現可能なpass/fail対象にはできるが、独立一次根拠で確認済みの`confirmed`とはみなさない。

### 5.11 プロジェクト仮定

既存Phase 1モデルの式を、安定したID、明示式、入力、適用範囲、感度、内容SHA-256とともに固定した数量規則。外部集計値へ合うよう逆算・校正せず、内容変更時は新versionとして基準fixtureを再審査する。

### 5.12 等価体力差分

実機内の連続消費、宿舎回復、瞬時の体力交換を、勤務枠ごとの符号付き体力変化量へ正規化した値。Phase 1では実機イベント列ではなく、始端・終端体力、上下限、枠間連続性、同時配置制約、周期閉包を検証する。

### 5.13 Normalized-theoretical benchmark

ゲーム内在庫の実測値ではなく、固定した施設、schedule、支援資源、除外事項のもとで算出する理論比較ケース。本仕様では、順序付き36時間全循環の先頭2勤務枠を具体的な連続24時間評価窓として評価することを意味する。36時間全循環の自然生産平均を24時間へ換算することは意味せず、その値を先頭24時間の実値として扱ってはならない。

### 5.14 Support-resource scenario

通常optimizerへ任意で渡す、勤務枠別の固定支援resource入力。source operatorの所有、地域利用可能性、施設slot、同時operator競合は通常制約として厳密に検証する。勤務枠内のmorale閾値や回復を固定化した場合、その簡略化をfixture、固定provenance、仮定bundleへ記録する。解決不能なsourceを0として扱わず、typed diagnosticを返し、不完全なbenchmarkを合格させない。

## 6. Phase 1の固定条件

### 6.1 基地構成

- レイアウト: 243
- 貿易所: 2室
- 製造所: 4室
- 発電所: 3室
- 各施設は、対象バージョンで243基地として成立する最大レベルを前提とする
- 製造品の主基準は金属2室・作戦記録2室とする
- 24時間評価窓の途中で製造品を切り替えず、全勤務枠で金属2室・作戦記録2室を維持する
- 制御中枢、宿舎、応接室その他の支援施設は、製造・貿易の計算に関与する範囲で完全な基地コンテキストへ含める
- 現行型で直接表現できない施設種別・施設レベルが必要な場合、暗黙の最大値で代用せず、型または明示的な基準ケース入力として表現する

### 6.2 所持・育成条件

主ケース:

- 対象地域・対象バージョンで利用可能な全オペレーターを所持
- 各オペレーターは、その基地スキルがすべて解放される昇進段階・レベル
- 潜在・モジュールは、基地スキルまたは基地生産へ影響する根拠が確認された場合だけ考慮する

追加ケース:

- 外部資料で条件が明示された限定所持ケース
- 高価値な組み合わせの一部を未所持とした退行ケース
- 低レア中心など、同値性と探索のフォールバックを検証できる代表ケース

### 6.3 ローテーション

- 採用編成: 内容SHA-256で固定したWikiru backup 38の12時間variant
- 評価期間: 順序付き36時間全循環の最初の勤務枠を`t=0`とする、先頭2勤務枠の具体的な連続24時間
- Wikiruの勤務グループ色を固定IDへ対応させ、全循環の勤務枠を`groups-a-b`、`groups-b-c`、`groups-c-a`の順とする
- 知覚情報製造組はproduction group Cであり、`groups-a-b`では非稼働、`groups-b-c`では知覚情報20、`groups-c-a`では知覚情報10として評価する
- したがって先頭24時間の資源値には`groups-b-c`の知覚情報製造組だけを含め、`groups-c-a`の寄与は24時間値へ含めず36時間全循環の持続可能性証人にだけ使用する
- 基準勤務モデル: 12時間×2勤務枠、または8時間×3勤務枠
- いずれか一方へ適合すればよく、両モデルの基準ケースを同時に要求しない
- 開始境界: オフセット付き絶対日時、または固定出典内の順序付き勤務枠ID。根拠のないカレンダー日時を作らない
- 全循環周期は24時間を超えてよいが、出典に周期全体が明示されていること
- 全循環平均を24時間換算して、具体的な24時間評価窓の値の代用にしてはならない
- 同一オペレーターを同一シフト中に複数配置してはならない
- 隣接勤務枠の勤務者は原則として重複させない
- 例外がモデル上成立する場合は、外部根拠または固定したプロジェクト仮定と、体力状態遷移を基準ケースへ明記する
- 勤務消費、通常回復、体力交換は、勤務枠ごとの符号付き等価体力差分へ正規化する
- 各オペレーターの始端・終端体力、同時配置、上下限、枠間連続性、全循環終端の閉包を機械検証する
- `normalized-theoretical`ケースでも36時間canonical cycleと全3勤務枠を保持し、資源台帳の24時間値は先頭2勤務枠だけから算出する

### 6.4 固定support-resource scenario

- 完全な支援施設simulationがPhase 1に対して過剰な場合、複雑なresourceをwindow内一定として固定できる
- 固定sourceはoperator ID、地域、施設、slot、active window、resource、amount、provenanceを持つ
- source operatorは所有・地域・同時配置制約を満たし、実slotを予約する
- 固定sourceと寄与量は、固定した一次skill dataまたは許可されたプロジェクト仮定から導出し、仮定を使う場合は`assumptionBundle.allowedAssumptionIds`に含める
- expected outputやreference team IDから固定resource量を逆算してproduction scoreへ渡してはならない
- operator名、fixture ID、reference compositionを分岐条件としてproduction scoreへhardcodeしてはならない
- 固定寄与はscoring contextとplanの資源台帳・evidenceへexactly once記録し、二重計上しない
- 未所持、地域未実装、slot不足、同時再利用、provenance不備はtyped diagnosticとしてfail closedにする
- 通常Appでscenarioが未指定の場合、既存動作を変更しない。Phase 1ではscenario設定UIを追加しない
- Wikiru caseの勤務枠対応は本書6.3をauthorityとし、`groups-a-b`はproduction group C非稼働、`groups-b-c`は知覚情報20、`groups-c-a`は知覚情報10とする。補足仕様の例が異なる勤務枠へ対応付けている場合、その例を採用しない
- 補足仕様は一般的なscenario input、source予約、diagnostic、evidenceの契約だけを補足し、本書の評価窓、全循環、資源台帳、持続性、confidenceおよび仮定許可範囲を変更しない

### 6.5 ドローン

- Phase 1では、各勤務枠で使用可能な全ドローンをその勤務枠の貿易所1へ固定投入する
- 24時間に利用可能なドローン量は、発電所構成、発電所スキル、初期値の前提から算出する
- 初期ドローン残量を利用する場合は、基準ケースへ明記する
- 投入先は外部集計値やモデル上の限界効率に応じて変更しない
- 連続期待値モデルで、自然回復分、初期在庫、使用量、終端在庫、特殊注文寄与を分離する
- 根拠が確定していないドローン挙動を、通常の受注効率へ単純加算してはならない

## 7. 最適化目的と成果指標

### 7.1 資源別実数量

24時間出力は、少なくとも次を別々の値として保持する。

- 生産した金属数
- 貿易所で消費した金属数
- 24時間終了時の金属純増減
- 生産した作戦記録の経験値総量、または根拠資料と一致するゲーム内単位
- 獲得した龍門幣
- 自然生産による量
- ドローン投入による追加量

異なる資源を、出典のない固定係数で単純加算して正解判定してはならない。

### 7.2 固定優先度ケース

基準データは、少なくとも次の目的プロファイルを独立ケースとして保持する。

- 龍門幣優先
- 作戦記録優先
- バランス

各ケースは次を明示する。

- 製造品構成
- 金属収支制約
- 比較する資源の優先順
- 最低生産量などの制約
- 同値判定方法
- 外部資料が用いた目的関数または選定基準

共通の隠れた単一スコアへ変換しない。目的プロファイル間で比較方法が異なる場合は、基準ケース側に明示し、コード側で追跡可能にする。

### 7.3 探索結果の決定性

同値候補が複数ある場合、出力を安定させるために決定的なタイブレークを用いる。タイブレークは生産量の正しさを変更してはならず、オペレーターIDなどの安定した値だけを使用する。

## 8. 外部根拠の方針

### 8.1 根拠の優先順位

1. 対象地域・対象バージョンのゲームデータ原文またはゲーム内表示
2. 公式告知・公式更新履歴
3. 詳細な式または検証手順を提示する日英中Wiki
4. 独立した計算表、最適編成資料、検証動画・記事
5. 式のない編成紹介や二次的なまとめ

理論編成と全循環は、出典固定された公開資料1件を最低条件とする。資源値は、その編成、版固定した一次ゲームデータ、明示式から独立再現する。JP資料を優先し、すべての条件へ適合するJP資料がない場合はCN資料を採用できる。同一編成を掲載する第2の独立資料は必須としない。

Wikiru backup 38の固定編成について、一次根拠だけでは数量化できない次の3領域に限り、固定したプロジェクト仮定で補完できる。

1. 高価値注文確率の勤務時間依存則
2. 知覚情報製造組の勤務枠別効率
3. 全循環の回復配置証人と等価体力差分

この補完を使うfixtureのconfidenceは`corroborated`とし、`confirmed`へ昇格させない。上記以外の未知効果は自動補完せず、未対応または`disputed`としてfail closedにする。

仮定bundle v1は知覚情報製造組を誤ってproduction group Bへ割り当てていたため、Wikiru backup 38の証拠パケットには使用しない。修正版はbundle v2として新しい内容SHA-256で発行し、v1は監査履歴として保持する。v2はproduction group C、`groups-a-b`非稼働、`groups-b-c`知覚情報20、`groups-c-a`知覚情報10を固定する。v2の受入前にv1を参照するfixtureを黙って読み替えず、再審査する。

### 8.2 資料間の不一致

資料間で値・解釈・適用順が食い違う場合:

1. 対象地域・バージョンの差を確認する
2. ゲーム原文と更新履歴を確認する
3. 再現可能な計算・検証手順を優先する
4. 解消できない場合は `disputed` として基準データに記録する
5. `disputed` な値を合格条件として固定しない
6. UI・計算で未対応効果を0として扱う場合は、未対応であることを警告可能な状態にする
7. 上記3領域の欠落だけは、固定済みプロジェクト仮定により`corroborated`な合否基準へ昇格できる

実ゲーム実測がないことだけを理由に、再現可能なnormalized-theoretical caseを`disputed`とする必要はない。一次skill data、公開schedule、固定scenario assumptionから独立再計算でき、除外事項と許容差が明記されている場合は`corroborated`とできる。ただし実ゲーム実測値と称してはならない。

normalized-theoretical caseを`corroborated`にできるのは、8.1で許可した3領域の補完に限る。support-resource scenarioは新しい根拠階層ではなく、一次skill dataまたは許可済みプロジェクト仮定を勤務枠へ渡す入力契約である。可変URL、外部集計値、期待編成、期待出力をscenarioのauthorityとしてproduction計算へ注入してはならない。

## 9. 計算モデル要件

### 9.1 スキル解放

- 昇進段階と必要レベルの両方を評価する
- 同一スロットの上位スキルは下位スキルを置換する
- 異なるスロットで同時に有効な効果は、ゲーム仕様に従って合成する
- JP未実装オペレーターをJPケースへ含めない

### 9.2 効率と生産量

- 基礎生産速度とスキル効率を分離して保持する
- 加算、乗算、上限、切り捨て、丸めの順序を根拠資料どおりに実装する
- 商品限定効果を汎用効率として扱わない
- 貿易所の受注速度、注文内容、注文確率、受注上限を区別する
- 製造所の製造効率、保管上限、製造品種を区別する
- UI表示用の概算効率を、資源実数量の正解値として流用しない

### 9.3 条件付き・施設間効果

次を独立して表現・検証する。

- 同一施設の指定オペレーター条件
- 別施設の指定オペレーター条件
- 所属・陣営条件
- 施設数、施設レベル、製造品数によるスケーリング
- 保管上限・受注上限によるスケーリング
- 制御中枢から製造所・貿易所への遠隔効果
- 発電所およびドローン回復への効果
- 宿舎配置によって生成・変換される特殊資源
- 他オペレーターの効率を無効化または変換する効果
- 同種効果の重複不可・高い方のみ適用するルール

JP factoryのsource-backed mechanicsは次を満たす。

- automation系の抑制は通常の同室製造効率を無効化する一方、skill原文が保証する施設数由来の製造効率は抑制後も有効とし、免除対象の寄与だけを分離して合成する
- Purestream、Weedy、EunectesとGreyy the Lightningbearerの発電所支援は、243の固定施設数と通常のremote effect経路から`+140%`を再現する
- Metalworkはoperator名ではなく版固定したskill-family metadataで表現し、Bryophyta、Gravel、Thorns the Lodestarの製造組とVivianaのsource-backed Knight条件は、通常のfamily scalingとremote effect経路から`+123%`を再現する
- Vivianaの対象判定を含む所属・family metadataは版固定した一次skill dataまたは明示overrideをauthorityとし、表示名、fixture ID、期待値による特例分岐を置かない
- これらの計算/data修正はsupport-resource scenarioやcomposition searchから独立して検証し、scenario入力を使って欠落metadataや誤った通常計算を補正しない

### 9.4 時間変化

- 時間経過で上昇・低下するスキルは、固定した連続期待値式または勤務枠単位の等価値で評価する
- 初回1時間、ウォームアップ、注文完了時、体力閾値などの境界を明示する
- `Math.trunc(shiftHours)` による暗黙の時間切り捨てへ依存しない

### 9.5 体力と回復

- 初期体力、基礎消費、制御中枢軽減、同室軽減、スキル補正を分離する
- 体力が尽きた後の効率を、根拠なくシフト全体へ適用しない
- 回復側の同時収容上限と、回復配置証人が使用するモデル上の支援条件を完全な基地コンテキストで評価する
- 勤務消費、通常回復、体力交換を、固定仮定bundleから導出した勤務枠ごとの符号付き等価体力差分として保持する
- 体力交換の実機内時刻、宿舎内の厳密な並び、勤務枠内の細かな回復段階は再現しない
- 24時間評価窓の外側も含む、出典に明示された全循環周期を検証し、周期終端から同じ運用状態へ戻れない編成を持続可能と判定しない

### 9.6 ドローンと特殊注文

- 24時間の自然回復量とスキルによる増分を算出する
- 貿易所へ投入したドローン量を追跡する
- 特殊注文、注文確率、追加龍門幣、金属消費量を別々に計算する
- ドローン投入で短縮された時間と受注効率を二重計上しない

## 10. ベンチマーク階層

原因を切り分けるため、次の順序でテストする。

### 10.1 レベル1: スキル単体

単一オペレーター、単一効果、固定施設コンテキストで、解放条件、効果値、対象商品、時間曲線、体力補正を検証する。

### 10.2 レベル2: 施設内チーム

同室条件、指定オペレーター、保管・受注上限、効率無効化、同種重複不可を含む2〜3人チームを検証する。

### 10.3 レベル3: 施設間連携

制御中枢、発電所、宿舎、応接室から製造所・貿易所へ影響する効果を検証する。

### 10.4 レベル4: 勤務枠

時間変化、体力消費、注文分布、ドローン投入を含む12時間または8時間の1勤務枠の資源実数量を検証する。

### 10.5 レベル5: 24時間ローテーション

2勤務枠または3勤務枠、等価体力差分、金属収支を含む、出典で開始境界を固定した具体的な24時間出力を検証する。

### 10.6 レベル6: 全基地理論編成

全員所持・全基地スキル解放条件と限定所持条件で、外部の理論編成および資源別理論値と比較する。

### 10.7 テストシーム

主テストシームは、チェックイン済みの基準ケースを一括で読み込み、勤務枠、24時間評価窓、全循環、完全な243施設配置、製造品、ドローン、出典固定、地域可用性、仮定bundle、資源台帳、等価体力差分を外部契約として検証する境界とする。

知覚情報製造組のシフト対応を修正するbundle v2では、次の3境界を必須とする。

1. bundle生成・検証境界で、v2のproduction group C、`groups-a-b`非稼働、`groups-b-c`知覚情報20、`groups-c-a`知覚情報10、version、内容SHA-256、決定的再生成を検証する。
2. producer-consumer互換境界で、実際のv2のID、version、内容SHA-256、許可仮定IDをPhase 1 strict fixture validatorへ渡し、受理されることを検証する。局所的なplaceholderだけでは互換性を証明しない。
3. Wikiru独立再現境界で、固定snapshotのシフト2・3配置、先頭2勤務枠の24時間窓、先頭24時間へシフト3の寄与を混ぜないこと、および36時間全循環証人を検証する。

provenance比較は、固定した参照根拠・一次データ・仮定bundleの不一致を診断する補助シームとする。独立再現スクリプトの保存済み出力とのbyteまたは数値一致を第2の証拠シームとする。実optimizer出力との数値比較は後続の精度ゲートで扱い、本境界では内部ヘルパーの実装詳細ではなく、基準ケースの受理・拒否・診断結果を検証する。

JP factory prerequisite seamでは、通常のcandidate/team計算境界でPurestream・Weedy・EunectesとGreyy the Lightningbearerの`+140%`、automation抑制下の施設数寄与、Bryophyta・Gravel・Thorns the LodestarとVivianaの`+123%`、Metalwork familyおよびKnight metadataをexactに検証する。operator名・fixture IDの特例を許さない。

support-resource scenario seamでは、scenarioあり・なしの両方を通常optimizer経路へ通し、勤務枠限定activation、source operatorとfacility slotの予約、所有・地域・同時再利用の拒否、typed diagnostic、資源台帳とevidenceへのexactly-once記録、入力順序に依存しない決定性、未指定時の既存App動作を検証する。期待出力またはreference compositionをcandidate scoringへ渡してはならない。

## 11. 原因分類

差分は最低限次のいずれかへ分類する。

- `source-data`: 原文・翻訳・数値・地域実装状況の誤り
- `interpretation`: スキル文言から構造化効果への変換誤り
- `calculation`: 加算順、確率、時間、体力、資源収支の計算誤り
- `search`: 正しい候補を生成できない、または探索枝を早期に捨てる問題
- `state-model`: 施設レベル、宿舎数、地域、時刻など必要状態を表現できない問題
- `reference`: 外部基準自体の誤記、版違い、再現不能

修正前に、失敗する最小の基準テストと原因分類を作成する。原因が確定するまでプロダクションコードを変更しない。

## 12. 受け入れ条件

### 12.1 基準データ

- JP適合ケースを優先し、適合するJP資料がない場合はCN適合ケースを採用する
- JPとCNの両ケースを同時に必須としない
- 各ケースに固定コミットまたは内容ハッシュ付き保存物、参照日、対象地域、バージョンまたは版境界、24時間評価窓の絶対またはsource-relative開始境界、期待編成、全循環、期待式、期待値がある
- 編成と全循環の固定出典1件、および版固定した一次ゲームデータがある
- 12時間×2勤務枠または8時間×3勤務枠のいずれか一方に適合する
- 24時間値は、出典に固定された具体的な連続24時間から導出され、全循環平均の24時間換算ではない
- `disputed` なケースは合格条件から除外される
- 固定した3領域のプロジェクト仮定だけで補完されたケースは`corroborated`として合否対象にできる
- 仮定bundleはID、version、内容SHA-256、式、入力、適用範囲、感度を保持する
- Wikiru backup 38の12時間variant、36時間全循環、先頭2枠の24時間窓を採用する
- bundle v2はWikiruのproduction group Cと勤務枠対応を保持し、v1の誤ったシフト対応を引き継がない
- テストはネットワークなしで実行できる
- JP normalized-theoretical caseを主gateとし、CN caseはsource conflict解消までsecondary/non-gatingとする
- normalized-theoretical JP gateも先頭2勤務枠の具体24時間を使用し、36時間平均の24時間換算値を使用しない
- optional support-resource scenarioは固定provenance、許可仮定、source予約、地域・所有・競合検証、資源台帳へのexactly-once記録を満たす。未指定時は通常App動作を変えない

### 12.2 計算精度

- 判明済みのスキル単体式は、基準式と厳密一致する
- 丸めが必要な場合は、丸め前内部値とゲーム表示値を分けて検証する
- JP gating caseの外部集計Gold・EXPは相対誤差0.1%以内とする。source/operator/window/resource amountなど離散条件は厳密一致させる
- CNを含む非gating caseはcase固有の許容差を保持し、JP合格のために値を補完しない
- 分母が0の項目は絶対誤差で判定し、その許容値をケースに明記する
- ドローン寄与と自然生産を二重計上しない

### 12.3 編成

- 公開理論編成または同値編成を選択する
- 同値編成の判定は、制約充足と資源別出力の許容差で行う
- 同一シフト内でオペレーターを重複配置しない
- 原則として隣接勤務枠間で勤務者を再利用しない
- 限定所持ケースで未所持オペレーターを選択しない
- JPケースでJP未実装オペレーターを選択しない
- referenceまたはoutput-equivalent planへ到達した実用探索は、global optimality未証明でも合格できる。ただし未証明をtyped `not-certified` diagnosticで明示し、最適性を主張しない
- partial planまたは空planを同値編成として合格させない

### 12.4 持続性

- 各勤務者が12時間または8時間の勤務枠を完了できる、または体力切れ後の挙動を正しく生産量へ反映する
- 回復側の同時収容制約と、固定仮定bundleから導出した等価体力差分が成立する
- 出典に明示された全循環周期の終端で、同じ運用状態へ戻れる
- 金属消費が初期在庫および生産量の前提を超えない

### 12.5 未対応効果

- 製造・貿易の理論値へ影響する効果を、警告なしに無視しない
- 未対応効果には機械可読な理由と影響範囲を付与する
- 未対応効果を含む基準ケースを、完全対応ケースとして合格させない

### 12.6 回帰と品質

- 既存の関連テストが成功する
- 新しい階層別ベンチマークが成功する
- 基地スキル監査が成功する
- TypeScriptビルドとViteビルドが成功する
- 同じ入力から決定的な結果を生成する
- ブラウザ内で実用可能な実行時間・メモリに収まる。具体的な性能上限は現行ベースライン計測後にチケットで確定する

## 15. 段階的な完了判定

### Gate A: 外部基準の確立

- Wikiru backup 38の12時間variantを、JPの基準編成として確立する

- 現行シミュレーターを基準ケースへ入力できる
- 編成差分と資源別数値差分を出力できる
- 差分を原因分類のいずれかへ割り当てる

### Gate C: スキル・計算精度

- 対象理論編成に関係する各スキルの単体・チーム・施設間テストが通る
- 12時間または8時間の勤務枠の資源別出力が基準値と一致する

### Gate D: 探索精度

- 正しい候補計算から理論編成または同値編成を探索できる
- 限定所持ケースでも制約違反がない
- unproven pruningを使用した場合はnot-certifiedを返す。reference/equivalent到達と全dimension充足を満たす限り、global optimality証明はPhase 1の必須条件にしない
- JP benchmark環境で10秒以内に完了する

### Gate E: 24時間評価と全循環持続性

- 2勤務枠または3勤務枠と等価体力差分を含む、開始境界固定の具体24時間値を使用する。JP gating caseのGold・EXPは相対±0.1%以内、その他の項目はcaseに固定した許容差以内とする
- 36時間全循環平均を24時間値へ換算してgateを通さない
- 出典に明示された全循環周期の終端で同じ運用状態へ戻れる
- 全検証コマンドが成功する

Gate Aから順番に進め、前段階の不確定要素を後段階の探索調整で隠さない。
